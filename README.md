# CoCo

CoCo 是面向个人使用的空中智能机器人助手：通过自然语言理解目标，由 AI Agent 协调线上操作与实体机器人的自主飞行、感知和机械操作。客户端包括 Windows、Ubuntu、macOS 三款桌面软件和一款 iOS App。目标称呼与唤醒方式为 `CoCo` / `Hey CoCo`。

**产品语言**　四端仅提供英文版，暂不提供中文版或语言切换。设计稿、实现和验收使用英文文案，覆盖界面标签、无障碍名称、任务状态、错误反馈及应用提供的权限说明。

**开源许可**　CoCo 的原创软件在 [ChiZhang-805/CoCo](https://github.com/ChiZhang-805/CoCo) 发布，采用 [Apache-2.0](LICENSE)。第三方材料遵循各自的许可。

**目标体验：**“CoCo, get me a boba tea and meet me at the library.” 系统在用户授权、商户配合和现实执行条件满足时，完成下单、路线规划、取货、携带、交付与反馈。这是产品目标，不是已实现能力。

## 在 Windows 上运行

安装 Node.js 24 后，在仓库根目录打开 PowerShell 运行以下命令。

```powershell
cd clients/windows
npm ci
npm start
```

在同一目录运行 `npm test` 可检查窗口交互，`npm run dist` 可在 `dist/` 生成 Windows x64 安装包。也可直接启动 `dist/win-unpacked/CoCo.exe`，此方式需要保留同目录的运行文件。

Windows 的 Maps 可离线浏览校园地图。地图卡片与底部页码同屏显示，宽屏采用四列三行，窗口较小时自动调整每页数量。卡片使用缩略图，Activity 和任务轨迹使用可缩放的矢量底图。选中卡片后可在 Activity 中平移、缩放和分享地图位置。地图信息按钮提供数据署名和许可。底图由 [OpenStreetMap 贡献者](https://www.openstreetmap.org/copyright)的数据绘制，源数据使用 ODbL 1.0 许可。

Tasks 的历史记录保留指令和状态时间线。点击详情或轨迹图标会打开右侧栏，可回放示例路线，也可查看已收到且落在同一内置地图内的连续定位。重跑按钮用原指令创建独立的本地 `Demo` 记录，仅用于预览。编辑会合点和 iPhone 点单入口位于聊天工具菜单。

## 系统范围

| 板块 | 职责与边界 |
| --- | --- |
| Agent 与任务 | 理解指令、拆解任务、调用工具、协调数字与物理执行；不直接承担实时飞控 |
| 语音交互 | 唤醒、语音识别、语音回复；保留点击说话与文字输入，不把目标唤醒方式写成已具备的平台能力 |
| 客户端 | Windows、Ubuntu、macOS 桌面软件和 iOS App 提供交互、任务、设备状态与授权入口，共享业务语义 |
| 数字操作 | 优先使用服务 API；确有需要时使用 UI Agent；在授权范围内完成查询、下单等操作 |
| 地图与导航 | 分析地图、规划路线、动态避障和目的地导航；地图路径不等于可直接执行的安全航线 |
| 感知与定位 | 以 GPS/GNSS 与视觉为主要方案，保留飞控所需惯性反馈；深度相机、雷达等按实际需求增加 |
| 飞控与安全 | 起降、姿态与运动控制，以及必要的电量、失联和异常处置；优先复用成熟飞控 |
| 机械与抓取 | 从零进行原创外形、机体与机械手的建模、制造和组装，实现抓取、提取、携带、放置，以及受控条件下拨开轻量障碍物 |
| 通信与协同 | 在 Agent、客户端和机载系统之间传递必要指令、状态与结果，避免重复执行支付或物理动作 |

**任务链：** 用户指令 → 任务规划 → 数字操作与导航 → 机器人执行 → 结果反馈。

跨端不重复建设完整的规划器、证据核验器和任务状态机。先实现当前需求的最小闭环；没有真实硬件或服务时使用明确标识的模拟，不把模拟结果当成真实能力。

**校园取送。** 桌面端发起任务，用户先保存会合点。接入高德或百度地图后可选择门店、校内入口并查看地面路线。需要更细的现场空间信息时，可采用三维地图，也可用获准采集的现场照片评估三维高斯泼溅重建。

点单优先交给 iPhone 上的商户入口，用户在那里确认金额和支付。接入移动端 UI 操作时，针对实际设备和商户应用验证可执行的步骤。桌面分别显示用户回填的取货信息、商户确认和机器人反馈。现场购买作为另一种履约方式，需单独验证商户配合与设备能力。

## 视觉设计

### 官方图像依据

视觉方向以以下官方发布的图像为依据，而不是泛泛的“紫色科技感”。链接用于设计参考，不是允许直接打包电影素材的授权。

| 编号 | 官方材料 | 提取的视觉特征 |
| --- | --- | --- |
| R1 | [Disney 电影页][disney] · [电影海报原图][poster] | 深紫蓝城市与橙金花桥的冷暖对比，局部洋红和亮蓝灯光 |
| R2 | [Disney 制作说明][lighting] · [花桥与城市剧照][bridge] | 橙色发光路径、层叠空间、冷色远景与暖色近景 |
| R3 | [Pixar 电影页][pixar] · [城市场景原图][city] | 蓝紫色环境、柔和雾光、疏密有序的彩色光点 |
| R4 | [Pixar 电影页][pixar] · [花车概念设计原图][concept] | 手绘线条、透明水彩式色块、纸面留白与轻微不规则轮廓 |
| R5 | [Disney 电影页][disney] · [片名字标原图][title] | 厚重的大写字形、圆形字腔、装饰性轮廓，以及红橙、金黄、洋红、亮蓝的分区配色 |

**提取口径：** 色系、字形特征和画风来自对官方图像的视觉归纳。下面的 HEX 是面向界面的人工适配值，未经原图像素级取样，不是 Disney/Pixar 发布的标准色号。界面用途、字号、圆角和动效规则均为本项目设计选择。

### 配色

主关系为**紫蓝夜色底 + 万寿菊橙主操作 + 金色高光**，洋红与亮蓝只作少量点缀。不是所有区域都高饱和，也不是把整张电影海报铺作背景。

| 设计变量 | HEX | 用途 | 依据或性质 |
| --- | --- | --- | --- |
| `background` | `#171225` | 页面背景 | R1/R3 的深紫蓝夜色，降低亮度后的 UI 适配 |
| `surface` | `#241B3B` | 卡片、面板、浮层 | 从夜色关系延伸的界面层级色 |
| `text` | `#FFF4E4` | 主文字、重要图标 | 为可读性新增的暖白，不声称来自采样 |
| `text-muted` | `#B9ABCC` | 次要文字、辅助状态 | 为可读性新增的浅灰紫 |
| `primary` | `#FF9E24` | 主按钮、当前任务、主要操作强调 | R1/R2 的花桥橙，UI 适配 |
| `gold` | `#FFD166` | 少量高光、品牌插画光源 | R1/R2 的金色亮部，UI 适配 |
| `violet` | `#8146C8` | 品牌装饰、选定容器的辅助强调 | R1/R3 的紫色光影，UI 适配 |
| `magenta` | `#EF3C96` | 插画与品牌小面积点缀 | R1/R5 的洋红，UI 适配；不默认用于正文 |
| `cyan` | `#12B5D0` | 焦点、信息强调、少量冷色点缀 | R3/R5 的亮蓝关系，UI 适配 |
| `success` | `#66D6A3` | 成功状态 | 工程语义补充色，不属于电影提取色 |
| `danger` | `#FF6B6B` | 错误与危险状态 | 工程语义补充色，不属于电影提取色 |

使用约定：

- 主按钮采用 `primary` 底与 `background` 色文字；不要使用橙底白字。警告可复用 `primary`，但必须附图标或短文字区分语义。
- 正文使用 `text` / `text-muted`；洋红、渐变、纹理和光晕不承担正文信息。
- 颜色与字号在实际采用的主题文件中集中管理，不逐页面复制；不为此额外搭建通用主题平台。
- 普通文字对比度至少 4.5:1；必要的控件识别信息与状态图形至少 3:1，参照 [W3C 文字对比度][contrast] 与 [非文字对比度][nontext]。状态不能只靠颜色表达。
- 纯色计算示例：`text` / `surface` 约 14.91:1，`text-muted` / `surface` 约 7.54:1，`background` / `primary` 约 8.84:1。透明度、图片叠加、禁用及其他交互状态仍需在实际界面检查；这些数值不等于完整 UI 已验收。

### 字体与字标

官方片名字样应按**专门设计的字标**理解。Michael Doret 的[作品资料][doret]将相关工作列为电影 Title Treatment；[Letterform Archive 的馆藏说明][letterform]展示了其设计探索。没有足够依据把片名字形认定为某个可直接用于正文的“官方 COCO 字体”。

| 层级 | 项目选择 | 用法 |
| --- | --- | --- |
| 产品字标与英文短标题 | `Nunito`，字重 700/800 | 取圆润、厚实和亲切感；不用电影字标的现成轮廓、花饰与排色布局 |
| 英文界面正文与标签 | `Noto Sans SC`，字重 400/600 | 保持清晰；不把装饰性字形用于任务、地图、支付或设备数据 |
| 字体不可用时 | 平台系统无衬线字体 | 不阻塞交互，不擅自引入来源不明的“电影同款字体” |

`Nunito` 是本项目选用的替代字体，不是电影字体；其圆润端点特征见[Google Fonts 字体说明][nunito-description]。`Nunito` 与 `Noto Sans SC` 的许可见各自官方仓库：[Nunito][nunito-license]、[Noto Sans SC][noto-license]。实际引入字体时保留相应版权与许可信息；许可文件不属于冗余审计文件。

排版起点：正文约 16、短标签约 14、页面标题约 24 个逻辑尺寸单位，按平台映射为对应单位；支持系统字号缩放。装饰性字标不承载状态信息。Windows 构建随应用打包所用字体的拉丁字符子集与许可，支持离线显示英文界面。

### 绘画风格与界面转化

必须区分**电影成片、概念画和字标**，不要把整部电影概括成单一水彩画风。

| 层面 | 官方图像观察 | CoCo 的应用方式 |
| --- | --- | --- |
| 角色与空间 | R1/R2：立体体积、柔和轮廓、暖冷光照与纵深 | 原创机器人插画采用简化的立体或 2.5D 表现；暖橙内光配紫蓝阴影 |
| 概念插画 | R4：松动线稿、透明色块、纸面留白 | 仅用于需要的欢迎图、空状态或轻量插画；不把纸纹铺到表格和控制面板 |
| 装饰形状 | R5：厚实轮廓与节庆式色块 | 转为少量原创几何装饰，不照描电影花饰、吉他或现成字标 |
| 功能图标 | 属于项目界面设计，不是电影提取物 | 使用同一套简洁、圆角的图标；约 24 的逻辑尺寸，保持线宽一致 |
| 控件与布局 | 属于项目界面设计 | 控件圆角约 12、卡片约 20，间距以 4 为基准；优先信息层级而非装饰 |
| 动效 | R2 的柔光提供气质参考；时长为项目自定 | 唤醒时轻微亮起、完成时短促反馈；一般过渡约 160–240 ms，支持减少动态效果 |

主界面围绕**语音入口、当前任务、机器人状态**组织。使用图标或“图标 + 简短文字”，不要增加功能教学段落、营销文案和无用说明卡片。图标保留可访问名称；支付授权、危险操作、故障与必要引导仍需清楚表达。

避免全屏持续粒子、到处发光的边框、彩虹渐变卡片、每个模块一种亮色、装饰字体正文，以及为了展示主题而建立无功能页面。功能界面保持简洁，电影气质主要由配色关系、局部插画和少量柔光承载。

机器人、App 图标与产品字标采用原创设计；不把官方剧照、角色、电影 Logo 或音乐直接作为产品资产。`CoCo` 是本项目名称，不表示与电影出品方存在关联或已获得名称、商标和素材授权。

## 开发规范

1. **避免无用审计文件。** 不创建阶段汇报、证据报告、决策快照、重复总结或备份副本；保留真正用于运行与排障的记录。
2. **避免过度防御性编程。** 在输入、权限、支付、外部服务和物理安全边界校验；内部按清晰契约协作，不重复检查、吞掉异常或堆叠兜底。
3. **避免无依据的终止条件。** 不随意叠加超时、重试与退出分支；保留确有依据的资源预算、任务结束与安全处置，不允许无限重试。
4. **减少说明性文字。** 注释解释非显然约束；文档记录必要约定；界面不堆砌描述。代码逻辑、状态和错误应直接表达事实。
5. **简化 Evidence 核验。** 订单返回、设备反馈、夹爪状态等直接结果优先；不默认进行多模型复核或构建复杂证据链。
6. **精简结构化通信。** 只传下游执行所需字段；不默认携带完整对话、模型推理或无关历史。必要的坐标系、单位、时效和授权信息不能省略。
7. **目录清晰。** 按实际职责组织；不预建空目录，不为简单功能拆出多层抽象或并行架构。
8. **命名简洁准确。** 自有文件与文件夹不加日期、版本号或 `new`、`old`、`final`、`backup` 等后缀；遵循所用语言与平台习惯。
9. **原地迭代并清理。** 直接修改已有文件，按需新增、删除，并清理失效引用、依赖和资源；保留仍有用途的用户数据、迁移与兼容路径，历史交给 Git。
10. **UI 极简但可理解。** 优先图标，存在歧义时配短标签；不以去掉必要状态、授权与风险信息换取表面简洁。

**共同约束：** 优先复用成熟 API、算法、框架和飞控；不为“从零造机器人”而重写所有底层能力。只增加当前任务需要的依赖与抽象，先跑通最小端到端流程，再针对真实瓶颈扩展。

日期、版本、开发进展和增删改集中记录在 `CHANGELOG.md`。这限制的是自建迭代记录，不应误删程序必需的依赖版本、锁文件、运行时间戳、工具要求的迁移记录或第三方原始文件名。

## 实施边界

- **平台能力：** iOS 的自定义唤醒与后台执行必须分别验证；App Intents/Siri 接入不等于获得第三方系统级常驻唤醒能力。以 [Apple App Intents][app-intents] 和[后台执行文档][background-modes]为依据，不用不当后台保活伪装已实现。
- **数字权限：** 登录、账户访问、支付和外部数据访问应在用户授权范围内；不绕过验证码、账户权限或平台限制，不默认记录敏感原文。
- **物理执行：** 高层 Agent 给出目标，专门模块完成实时控制；保留避障、电量、失联、载荷和抓取反馈。取消任务不等于直接关闭空中电机。
- **真实任务：** 先模拟，再受控验证；真实飞行与取货必须具备适用的场地、运行许可、商户配合及载荷条件。没有硬件验证时，不宣称已完成实体任务。
- **客户端技术选型。** Windows、Ubuntu 和 macOS 桌面端采用 Electron，复用相同的界面和交互，各平台负责自己的窗口适配、构建与分发。iOS App 独立开发，通过核心接口共享任务语义。

### 四端工程内部

界面先以设计图评审，确认后再写界面代码。Windows 主窗口采用自定义标题栏，与工作区周边和左侧导航共用纯色外壳背景 `#F2F2F4`。标题栏左侧依次放置后退、前进和侧栏开关，中间留作拖动窗口的区域，右侧依次放置最小化、最大化／还原和关闭控件。下方白色工作区右上角留白，有具体功能时再加入相应操作。

Windows 侧栏左下角显示当前用户的头像和姓名，设备连接状态显示在 `Devices` 项下。模拟用于开发测试，面向用户的主界面只提供实际功能入口。

下图适用于 `clients/windows/`、`clients/ubuntu/`、`clients/macos/`、`clients/ios/`。工程清单和构建入口放在各端根目录。工具链有原生约定时直接采用其布局，例如 Apple 工程可用资源目录和测试 target 承担下图职责。

```text
<平台>/
├── src/                 启动、生命周期与核心接口调用
│   ├── ui/              指令输入、当前任务、授权确认与设备状态
│   └── system/          系统音频、麦克风权限与平台专属入口
├── resources/           安装图标、应用资源目录等平台专属输入
├── packaging/           需要单独维护的安装、签名或分发配置
└── tests/               本端交互、系统接入与启动测试
```

| 平台工程 | 本端专属内容 | 构建负责人交付与验证 |
| --- | --- | --- |
| `clients/windows/` | 桌面窗口、音频设备选择、Windows 安装配置 | 构建桌面程序和安装包，在 Windows 上验证安装、启动、任务提交与卸载 |
| `clients/ubuntu/` | 桌面启动项、系统音频、发行包依赖 | 构建可安装的桌面软件，在目标 Ubuntu 桌面版本验证安装、从应用菜单启动及任务提交 |
| `clients/macos/` | 窗口与菜单、麦克风权限声明、桌面分发配置 | 构建可启动的 `.app`，在 Mac 验证任务提交和权限；对外分发时验证签名后的交付物 |
| `clients/ios/` | 触控界面、前后台切换、麦克风权限、按需接入的 App Intents | 构建 iOS App，在模拟器验证交互，在 iPhone 验证安装、音频权限和前台恢复 |

安装清单、签名配置等已由原生工程承载时直接在原处维护。可分发的安装包和编译缓存使用构建工具的输出目录。`packaging/` 只收录制作交付物所需的源文件。

### 跨目录归属

- **任务与授权。** 客户端显示授权内容并回传用户选择，`core/tasks/` 判断这次操作是否获准，`core/digital/` 负责按该授权调用服务并处理返回结果。四端都从同一接口取得任务状态。
- **机载执行。** 例如“去取货”是任务目标，经过 `robot/link/` 进入机载软件。`perception/` 提供位姿和障碍观测，`navigation/` 计算路径，`flight/` 按飞行约束决定能否执行。Ubuntu 桌面端展示这些结果，机载代码统一放在 `robot/`。
- **夹爪与制造。** 夹爪模型、加工图和夹持力试验方法跟随 `hardware/gripper/`，控制程序及传感器反馈放在 `robot/gripper/`。机体零件同样就近保存设计与制造文件，跨部件的安装关系、整机载荷和重心验证归 `hardware/assembly/`。
- **共享资源与测试。** 同一视觉资源被多个端使用时，原件和许可放在 `clients/assets/`，各端工程引用或在构建时转换。单端测试跟随本端，模拟数据跟随使用它的测试。跨模块场景才进入 `tests/integration/`，例如从客户端提交目标，经核心派发，由模拟机载端回传结果。

## 文档与 Codex 使用

`README.md` 保存稳定需求和规范；`CHANGELOG.md` 是唯一集中迭代记录；`PROMPT.txt` 是可复制给 Codex 的开发指令，不是另一份进展报告。

在本地打开项目后，将 `PROMPT.txt` 全文交给 Codex，并填写末尾的“本次任务”。仅把文本文件放进目录，不应假定它会自动加载。Codex 官方说明的自动指令机制另见[项目指令文档][codex-instructions]；本交付不额外创建重复规范文件。

每次完成可发布的改动，运行相关检查，更新 `CHANGELOG.md`，将本次改动提交并推送至 GitHub 对应分支。项目要求变化时修改本文，不在这里累积开发历史。
